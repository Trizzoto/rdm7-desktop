# Tonight, in the car — the CAN check

The one thing in the telemetry chain that has never been proven against real
traffic is the puck's **bit extraction**: does a channel you configure actually
pull the right bits out of a frame the car is really sending. Everything around
it is verified on hardware — the RPCs, the channel table, its persistence, the
record shape, the download, the decode in Studio. This is the last piece, and
it needs an engine running.

The puck was flashed at **2026-07-30 ~17:0x** with the firmware that carries
the bus scanner, live channel values, and the GNSS fix below. Studio is on the
matching build.

---

## Before you drive: prove the decode standing still

You do not need to move the car for the important part. Idling in the driveway
is enough to prove or disprove a decode.

1. **Wire the puck to the car's CAN.** High to High, Low to Low. It only
   listens — it never transmits onto the car's bus except its own RDM block at
   0x400–0x40F, which you can move in Setup → CAN bus if something there
   already uses it.

2. **Studio → GPS → Setup → Channels → Scan the bus.**
   You should see a list of ids with rates. If it says *nothing heard*, the
   three things that are actually wrong are named on screen: High/Low swapped,
   no termination, or the bitrate not matching the car (it is set to
   **500 kbps** — a Haltech is usually 1 Mbps on the main bus, so check this
   first).

3. **Find your signal.** Blip the throttle and press *Scan again*. The frame
   whose bytes change is the one carrying RPM. The panel shows the last eight
   bytes of each id, so you can watch which byte pair moves.

   If you already have a Haltech DBC, skip this: **Import a DBC…** and every
   signal in it arrives named, with the bit positions the file specifies.

4. **Make the channel.** Press **Use** on that frame — the form opens with the
   id filled in. Set the start bit and width for the signal, then Save.

5. **Tick Log, press Send.** This clears the puck's recording ring (the record
   changes size), so do it before you drive, not after.

6. **Watch the Live column.** With the engine running it should show a real
   number, updating twice a second, scaled the way you defined it. This is the
   whole test:

   | What you see | What it means |
   |---|---|
   | A number that tracks the throttle | The decode is right. Go and drive. |
   | `quiet` | The frame is not arriving — wrong id, or the ECU only sends it under some condition. |
   | A number that moves the wrong way, or is wildly out | Start bit, width, or byte order is wrong. Try Motorola instead of Intel first; it is the most common cause. |
   | Pegged at 0 or at maximum | Width is wrong, or the signal is signed and set as unsigned. |

Getting this right in the driveway is the difference between a useful drive and
a wasted one.

---

## Then drive

- **Nothing to press.** The puck logs from the moment it has power, and only
  above about 8 km/h; below that it deliberately logs nothing, so a stationary
  car produces an empty download and says so. (*Pause logging* exists for the
  bench, and a power cycle undoes it.)
- Check the card at the top of the Session aside says **Ready to record**. If
  it does not, it names the one thing that is wrong and carries the button
  that fixes it — most often **On the node**, which must show the track you
  intend to time against. That row exists because Studio's library and the
  puck's own memory are different computers.
- Afterwards: **Download from node**. The channel lanes appear in the rack
  named and scaled, and the recording now keeps them through a save, a reload
  and an export.

## If the GPS goes quiet

This happened three times on the bench today and is now root-caused: the trace
writer erases flash while recording, a flash write stalls any interrupt handler
living in flash, and the GNSS UART's handler was one of those — so its receive
FIFO overflowed and the driver jammed. Fixed three ways (handler moved into
IRAM, overflows now flushed the moment they happen, five-second watchdog kept
as a backstop).

**If it still happens**, Studio will say *receiver quiet* rather than showing a
stale fix. Two rows on the Monitor's **Satellite receiver** card now tell you
whether the old fault is back — both should stay at zero:

- **Receiver data lost** (`rx_overflow`) — the receiver's data overflowed and
  was flushed. A few is survivable; a climbing count means the flash
  contention is back.
- **Receiver restarts** (`rx_recover`) — the port had to be rebuilt outright.
  This should never happen now.

Note those two numbers before restarting — they are the difference between
"fixed" and "fixed the symptom". Then **Setup → Restart the node**: a real
hardware reset over the USB control lines, no plug-pulling. The recording,
the track and every setting survive it; the receiver bring-up reruns at boot.
(Proven 2026-07-30: a receiver that had been quiet for an hour with both
counters at zero — the watchdog task itself wedged — came back to a 15-sat
3D fix seconds after the reset.)

---

## What is still unproven after tonight

Nothing else in this chain, if the Live column shows a sane number and the
downloaded lanes match what the car was doing. If a lane comes back wrong
*after* the drive but the Live column was right beforehand, that is a
recording-path problem rather than a decode one, and worth saying so — the two
have completely different causes.

## Tomorrow: the dash on the same bus

The dash at **192.168.4.68** (`RDM-1CDB-D444`) was reflashed at
2026-07-30 ~21:30 with the decode-only firmware — it no longer times laps
itself, it only reads the puck's broadcast (ADR-0008).

**Its decode is already proven, on that physical dash, without a car.** The
firmware carries `POST /api/can/inject`, which feeds a synthetic frame through
the *real* receive and decode path. Sixteen fields were pushed through it and
all sixteen came back exact:

| Frame | Fields checked |
|---|---|
| `0x407` lap | current, last, best, lap number |
| `0x408` sector | sector time, theoretical best, sector number |
| `0x409` delta | signed delta (−0.42 s round-tripped signed) |
| `0x400`–`0x403` | fix, satellites, lat, lon, speed, heading, altitude, accuracy |

Auto-bind was proven too: one status frame identifying as an RDM GPS wired all
eight Position & GPS channels to the right frame ids, and **the bindings
survived a cold reboot**, so this is a one-time event and not something to
redo at the track.

So when the two are wired together, exactly **one** new thing is being tested:
that frames physically leave the puck, survive the wiring, and are accepted by
the dash's hardware filter. Everything about interpreting them is already
verified.

That narrows the diagnosis if lap time stays at 0:00.00 on the dash:

| What you see | Where the fault is |
|---|---|
| Dash shows 0:00.00, puck shows laps in Studio | Wiring, termination, or bitrate — not decode |
| `bus_errors` in the dash's info keeps climbing with both connected | Nothing is acknowledging — a physical bus fault |
| Dash shows lap times but the numbers are wrong | Base id clash — something else is using 0x400–0x40F |

The dash's `bus_errors` counter read 35 million before this, which is just
what a dash transmitting into a bus with nothing to acknowledge it looks like.
It should sit near zero once the puck is on the other end. If it does not,
that is the wiring, and no amount of software will fix it.

**One caveat worth knowing:** the dash still reports its version as `1.1.30`,
unchanged, because a version number is a release decision and this was a bench
flash. Do not read "1.1.30" as "the released build" on this particular unit.
