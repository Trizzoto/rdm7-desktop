## Governance

**James is the only person who edits this file.** Tommy, Cowork and Claude
Design all consume it. None of them edit it.

This is not about authority. It is about there being exactly one current
version. Two people editing the same specification produces two versions of it,
which is the problem this file exists to solve.

### Proposing a change

Do not edit this file to propose a change. Send James a change request:

1. **Section and token.** Which part of the file.
2. **Current value**, exactly as written here.
3. **Proposed value.**
4. **Why.** A measurement, not a preference. Contrast ratios against every
   ground the value will sit on, call-site counts, or a named constraint.
5. **What it affects.** Which surfaces, and roughly how many call sites.

### When a change is accepted

James verifies, decides, edits, and bumps the version. Then, in the same
sitting:

1. Adds a row to the change log below.
2. **Reissues the complete file to every consumer.** Tommy, and the Cowork
   session. Never a patch. The complete file, every time, so there is never any
   question about what is current.
3. States the version number in the message, not just the attachment, so it is
   findable by scrolling back.

**An edit that has not been reissued is not done.** A version sitting only on
James's machine is worse than no change at all, because two people are then
building against a specification that silently differs.

Any tool or assistant that helps James edit this file must remind him to reissue
it before the task is considered complete.

### Checking you have the current version

The version and date are in the header above. If yours is older than the last
version James sent, stop and get the current one before writing code against it.
Implementing against a stale specification is how drift starts.

## How to read this

Every token carries a provenance note:

- **inherited** — lifted unchanged from the existing codebase
- **corrected** — an existing value moved to fix a measured contrast failure,
  with the before and after ratio given
- **consolidated** — several near-identical existing values collapsed into one
- **new** — did not previously exist, with the reason

Of the tokens below, the large majority are inherited. Anything not inherited
says why.

# 1. Brand

## 1.1 Name

The company name is always **Realtime Data Monitoring**. "Realtime" is one
word. Never "Real Time".

## 1.2 Red

`#d2232a` is the brand red and the master value.

The two logo files currently disagree with it and with each other
(`RDM_Logo_Only_Vector.svg` is `#d71900`, `RDM_Full_Logo_Vector.svg` is
`#E01616`, ΔE 17.7 and 13.8 from master and 6.2 from one another). **Both logo
files are to be re-exported at `#d2232a`.**

`RDM_Logo_Only_Vector.svg` also contains a live `<text>` element rather than
outlined paths, so it renders in a fallback face wherever the typeface is not
installed. It must be converted to outlines before use.

A fourth red, `#CC0000`, is in production on the storefront (265 uses) and in
every marketing email. It is not a brand red and is mapped to `accent` in §11.1.

## 1.3 Voice

Tagline: **Realtime Data. ZERO Compromise.**
Descriptor: **A dash built by car people.**

- Short sentences. Australian spelling. Specific numbers. Paddock vernacular.
- Never use em-dashes. Use commas, colons, parentheses, hyphens, or a new
  sentence.
- Banned words: solutions, seamless, elevate, unlock, empower, game-changing.
- Approved claim wording: "no subscription required", "free to use, no
  licence", "free firmware updates over Wi-Fi". Never "lifetime", "always
  free", or "open source".
- Never imply third-party validation. Tommy's car is "the car the dash gets
  developed on".
- Real cars and real weather only. No stock footage.
- Do not build content on night mode, USB connection mode, rotation
  persistence or persistent peaks. None are live features.

# 2. Colour

## 2.1 Principles

1. **Roles, not values.** Code references a role (`text.primary`). Modes supply
   values. No component defines its own colour.
2. **No raw values in application code.** No hex, no rgba, no literal size.
   Anything new is added here first.
3. **Accent is a fill.** It needs 3:1 against its ground to be distinguishable.
   The 4.5 requirement lands on the label sitting on top of it, not on the fill
   against the page. Do not "fix" the accent by lightening it.
4. **Two text tiers only.** Three tiers cannot all clear 4.5 at 11px and 12px,
   which is where most of this interface lives. The former third tier
   (`ghost` / `hint`) is no longer a text colour.

**Accent fills on dark grounds.** `#d2232a` clears 3:1 as a fill only on grounds
at or below `#232323`. Measured: 2.52 on the dark `ground`, 2.21 on `surface`,
1.92 on `raised`, 2.70 on the device `raised`. Every dark ground in this file
sits above that boundary, so **an accent fill on a dark ground takes a 1px
`line.control` edge** to satisfy rule 3. The accent itself does not move.

## 2.6 Non-text contrast

Control outlines, focus rings and gauge arcs — anything a user needs to see to
identify or operate a control — require 3:1 against whatever sits behind them.
Use `line.control`.

Dividers and decorative rules are not control affordances and are exempt. They
use `divider` or `line.strong`, which are tuned for separation rather than
contrast and do not reach 3:1 by design.

Note that a red line at `#d2232a` on the dark `surface` `#393939` does not clear
3:1. Any accent line, ring or arc on a dark ground must use `accent.ink`
instead of `accent`.

# 3. Type

## 3.1 Families

| Role | Family | Applies to |
|---|---|---|
| Display and headings | Barlow Condensed | Studio, Dash web, Phone, Storefront |
| Body and UI | Barlow | Studio, Dash web, Phone, Storefront |
| Numeric and code | JetBrains Mono | Studio, Dash web, Storefront |

**Sora is removed** from Studio (54 CSS declarations, 2 `var()` fallbacks, 2
inline, 5 SVG, 50 canvas font strings including 49 via `GP_HUD_SANS`) and from
Dash web (9 declarations including `body`, 2 inline). This aligns the three
software surfaces with the Phone, which already runs Barlow and Barlow
Condensed (`Font.head` 254 refs, `Font.body` 190).

**The device keeps its existing fonts and is not changed.** It runs Montserrat,
Fugaz One, Manrope and a Barlow Semi Condensed TTF. Fugaz One is the dashboard
display face and stays. This is a deliberate exception, not drift: the device
is flash-constrained and the dashboard type is part of the product rather than
the interface chrome.

`Font.brand` (FugazOne) on the Phone has zero reads and is removed.

**Email cannot load webfonts reliably** and has its own fallback stacks — see
§13.5.

## 3.2 Scale

Eight steps. The ramp is tight because this is a dense technical interface, and
a wider ramp would force large visual movement across thousands of call sites.

| Token | px | Use |
|---|---|---|
| `text.xs` | 10 | dense labels, badges, table meta |
| `text.sm` | 11 | default UI label |
| `text.md` | 12 | body |
| `text.lg` | 14 | emphasis, list primary |
| `text.xl` | 16 | subheads |
| `text.2xl` | 18 | section headings |
| `text.3xl` | 24 | page titles |
| `text.display` | 32 | marketing and splash only |

**Fractional sizes are removed.** `8.5`, `9.5`, `10.5`, `11.5` and `12.5` were
nudges, not steps.

Nothing renders below 10px.

The storefront has four additional display steps above `text.display`. They are
storefront-scoped and do not apply to any application surface — see §13.2.

## 3.3 Line height and letter spacing

| Token | Value | Use |
|---|---|---|
| `leading.tight` | 1.2 | headings, single-line labels |
| `leading.base` | 1.45 | UI text |
| `leading.relaxed` | 1.6 | paragraphs |
| `tracking.tight` | -0.01em | `text.3xl` and above |
| `tracking.base` | 0 | everything else |
| `tracking.caps` | 0.08em | uppercase labels only |

43 distinct line-heights and 47 letter-spacings collapse to these.

The storefront and email add one wider tracking step — see §13.3.

## 3.4 Uppercase

Uppercase is for `text.xs` and `text.sm` labels only, always with
`tracking.caps`, always in Barlow Condensed. Never uppercase body text, and
never uppercase via `.toUpperCase()` in a render path, since that breaks
selection, search and screen readers. Use `text-transform`.

# 7. Motion

| Token | Duration | Use |
|---|---|---|
| `motion.fast` | 120ms | hover, focus, colour and border changes |
| `motion.base` | 150ms | the default for anything interactive |
| `motion.slow` | 300ms | panels, sheets, drawers, modals |

Easing: `cubic-bezier(0.2, 0.8, 0.2, 1)` as standard, `linear` for progress and
spinners only.

These are the two dominant existing values: 120ms appears 54 times and 150ms 30
times across Studio and Dash web, and `cubic-bezier(0.2, 0.8, 0.2, 1)` is
already in use. Thirty distinct durations and fourteen easings collapse to
these.

Never transition `all`. Name the properties. Dash web currently uses `all` 16
times.

**Reduced motion is mandatory.** Every animation and transition sits inside
`@media (prefers-reduced-motion: reduce)` handling. Studio has four blocks and
Dash web two; the Phone has none and needs `AccessibilityInfo` gating added.

# 8. Layout

## 8.1 Breakpoints

| Token | Query |
|---|---|
| `bp.sm` | `max-width: 640px` |
| `bp.md` | `max-width: 1024px` |
| `bp.lg` | `max-width: 1400px` |
| `bp.touch` | `(hover: none) and (pointer: coarse)` |

Breakpoints are expressed as `max-width` (desktop-first). A mobile-first
implementation may invert them to `min-width` at the same values; **the values
are the contract, the polarity is not.**

Dash web currently uses seven width breakpoints (1399, 1199, 1024, 780, 720,
640, 560) plus `max-height: 500px`. Those collapse to the four above.

Studio's `max-width: 900px` and `940px` blocks are **unreachable**:
`tauri.conf.json` sets `minWidth: 1024`, so the webview never renders narrower.
Delete them rather than migrate them.

# 9. Components

## 9.1 Rules

1. **One base per family**, extended by variant, never re-implemented.
2. **A variant used on one screen is not a variant.** It is a one-off and gets
   folded into the base.
3. **No raw `<button>` or `<TouchableOpacity>`** for anything that is a button.
   Studio and Dash web have 728 raw `<button>` elements between them; the Phone
   has 191 `TouchableOpacity` against 23 `ActionButton`.
4. **No native `confirm()` or `alert()`.** 21 call sites exist. They cannot be
   styled and will never match the system.

Current variant counts, which the work reduces:

| Family | Studio | Dash web |
|---|---|---|
| button | 24 | 19 |
| input | 17 | 28 |
| card | 21 | 17 |
| modal | 9 | 12 |
| nav | 32 | 22 |
| table | 13 | 29 |
| alert | 18 | 9 |

## 9.2 Required states

Every interactive component implements all of these. This is the largest gap in
the product: Dash web alerts have zero states, the Phone has zero pressed-style
functions and four selected props across the whole app.

| State | Treatment |
|---|---|
| default | base |
| hover | `highlight` overlay, `motion.fast` |
| focus | see 9.3 |
| active / pressed | `accent.pressed` fill, or `highlight` at double strength |
| selected | `accent` fill, or a 2px `accent` bottom border |
| disabled | see 9.4 |
| loading | spinner at `text.secondary`, control non-interactive, label retained |
| error | `status.danger` border and message, never colour alone |
| empty | `text.secondary` message plus a primary action |

## 9.3 Focus

`2px solid`, `outline-offset: 2px`, on every focusable element.

**The ring colour follows §2.2**, because a focus ring is a line:

| Ground | Ring colour |
|---|---|
| light | `accent` — 3.16 worst case |
| dark, including the device | `accent.ink` — 5.60 worst case |

`accent` as a ring on a dark ground measures 2.52 / 2.21 / 1.92 on the dark
`ground` / `surface` / `raised` and 2.70 on the device `raised`, all below the
3:1 in §2.6. **Studio currently uses `accent` in both modes and the dark case
changes.** Dash web currently uses blue and converts.

Inputs additionally swap `border-color` to the same colour by the same rule,
which Studio also already does on light.

**Danger controls are the exception.** A focused destructive button would be
red on red. Destructive controls take `2px solid text.primary` at
`outline-offset: 2px` instead — 8.20 worst case across all grounds.

Focus is never removed. `outline: none` without a replacement is a defect.

## 9.4 Disabled

`opacity: 0.45`, `pointer-events: none`, `cursor: not-allowed`, and
`aria-disabled`. Never communicated by colour alone.

## 9.5 Icons

One icon system per surface, sized on the type scale, colour inherited from the
parent text role. Never hardcode an icon colour. Icons appearing on more than
one surface must be the same asset, not redrawn.

# 10. Theming

## 10.1 Mechanics

Three settings: `system`, `light`, `dark`. Default is `system`. The OS
preference is followed and changes to it are picked up live.

The Phone already implements exactly this (`rdm.prefs.theme` in AsyncStorage,
`Appearance.getColorScheme()`, `Appearance.addChangeListener`). **The Phone is
the reference implementation.** Studio and Dash web adopt the same model.

Studio and Dash web currently persist no theme preference at all, so there is
nothing to migrate.

The device has no theme selection. It is dark.

The storefront has no theme selection either, for a different reason — see
§13.1.

## 10.2 The JS problem

Values read from JavaScript do not follow a `var()` swap. Dash web has 253 hex
literals across 205 lines in its JS region, and Studio has 50 canvas font
strings. Every one of these must be read from the token layer at paint time or
the theme toggle will leave them behind.

This is the single biggest implementation risk in the migration.

- **Device typeface.** The device runs no Barlow or Barlow Condensed. Its

# 13. Storefront and email

Two surfaces this file did not previously cover. Both are marketing surfaces
rather than application chrome, and both need additions the four software
surfaces do not. **Nothing in §13 changes an existing token.**

## 13.1 Grounds

The storefront's grounds are warm and high-contrast where the application
grounds are cool and mid-range. Neither set appears in the other.

| Role | Storefront paper | Storefront ink |
|---|---|---|
| `ground` | `#f3f1ee` | `#111111` |
| `surface` | `#ffffff` | `#1a1a1a` |
| `raised` | `#eceae6` | `#222222` |
| `sunken` | `#e4e2de` | `#0a0a0a` |

**Paper and ink are section contexts, not modes.** The storefront alternates
them within a single page; that alternation is the layout rhythm. There is no
theme toggle and §10 does not apply. Role names carry over unchanged — a
component inside an ink section resolves `text.primary` to the dark value.

**Do not lighten ink `raised` beyond `#222222`.** `accent` as a fill measures
3.04 against it, which passes by 0.04. Any lighter and the fill needs the edge
described in 2.1.

## 13.2 Display type

§3.2 stops at `text.display` (32px) deliberately, because a wider ramp would
force large visual movement across a dense technical interface. A shopfront has
the opposite requirement: its hero is the loudest thing on the page.

These four steps are additive. `text.*` is unchanged and remains the only scale
used by Studio, Dash web, Phone and Device.

| Token | Value | Use |
|---|---|---|
| `display.sm` | `clamp(28px, 3.2vw, 40px)` | section headings |
| `display.md` | `clamp(36px, 4.6vw, 64px)` | major section headline |
| `display.lg` | `clamp(44px, 6vw, 88px)` | hero; second line in `accent.ink` |
| `display.xl` | `clamp(56px, 8vw, 120px)` | campaign and launch heroes only |

Fluid rather than fixed because the storefront spans 390px to 1400px+, where
Studio has a hard `minWidth: 1024`. A fixed 90px headline does not fit a phone.

All four sit well above the 24px large-text threshold, so 3:1 applies to them,
not 4.5.

## 13.3 Tracking

| Token | Value | Use |
|---|---|---|
| `tracking.wide` | `0.18em` | mono eyebrows and uppercase button labels, storefront and email only |

The telemetry voice — `AUD $599 · SHIPPING NOW` — depends on open tracking.
`tracking.caps` at 0.08em loses it. 0.18em is the most-used existing value on
the storefront (16 occurrences) and matches the email button labels already in
production.

## 13.4 Spacing

| Token | px |
|---|---|
| `space.16` | 64 |
| `space.24` | 96 |

Marketing section rhythm runs at 64–96px against an editor panel's 48px
maximum. Both stay on the 4px grid. They absorb 133 existing uses.

## 13.5 Email

Email renders far more restrictively than the web and cannot use the token
layer at all.

- **No CSS custom properties.** Every value is inlined by hand. This file is the
  source; the email is a manual transcription of it.
- **Webfonts are stripped by most clients.** A Google Fonts link for Barlow
  Condensed is present in the current templates and does not survive, so those
  emails render in their `Impact` fallback. Set a deliberate fallback stack
  rather than inheriting one: `'Barlow Condensed', 'Arial Narrow', Arial,
  sans-serif` for display, `Barlow, Arial, Helvetica, sans-serif` for body.
- **Table layout, not flex or grid.**
- **No focus states, no hover, no motion.** §7 and §9.2–9.3 do not apply.
- **Every marketing email carries a physical postal address.** This is a
  deliverability and compliance requirement, not a style one.
- Email grounds are `#f3f1ee`, `#ffffff` and `#eae7e0`. All light-mode roles
  resolve normally against them.
- Buttons: `accent` fill, `accent.onFill` label, `radius.md`, `tracking.wide`,
  uppercase. Never an `accent.ink` label on an `accent` fill.
